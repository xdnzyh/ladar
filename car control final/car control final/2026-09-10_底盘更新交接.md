## 3. 合并时必须保留的行为

### 3.1 运动只执行一次，结果可以查询恢复

当前电脑端通过PING取得八位十六进制动作编号，发送带编号和CRC的MOVE。车停车后缓存本次结果并自动发送RESULT；回报丢失或损坏时，电脑只读查询同一个编号的停车快照，**不通过重新发送MOVE来恢复**。

```text
@PING,1234ABCD
@MOVE,W,718,CNT,1234ABCD,E06C
@RESULT,编号,方向,停止原因编号,请求值,单位,BRAKE,ENC,Q1,Q2,Q3,Q4,CRC
```

RESULT校验编号、请求、字段、CRC和运动学一致性后，才作为完成证据。原因编号0/1/2/3分别为TARGET/EMERGENCY/TIMEOUT/WRONG_DIRECTION。旧四字段MOVE及旧DONE接口保留兼容；新路径不能用未校验的旧DONE直接确认完成。

CRC及查询完整定义见 [RESULT1协议](control/结果恢复协议_RESULT1.md)。快照只保存最近一次动作，保存在RAM；重启后失效。不要把它当成可跨断电查询的动作历史库。

### 3.2 参数确认缓存与空闲预备握手

READ/APPLY成功后缓存参数确认状态，普通动作不重复读取95项参数。空闲时提前完成下一次PING，编号仅供下一次MOVE使用；准备完成后提交动作直接发送。正在准备时收到动作，则接管同一次PING。配置操作、自检、重启、急停及不确定状态须正确清理或排空预备状态。

实际日志中，请求到写出MOVE从约0.59秒降低至约0～3毫秒。该数字表示电脑端发送等待，不是车辆物理起步延迟。保留现有接收静默检查，避免配置、PING和结果查询交错。

### 3.3 配置丢报恢复的实现范围

**以下恢复策略目前已在C#参数工具和新集成终端实现，Python的 `chassis_config1.py` 尚未同步：**

- I/G读取失败时最多补发2次，每次读取使用新的查询标记，继续严格校验。
- B/S应答丢失时最多补发2次，保持相同事务及相同参数值。现固件对同事务B保留已有暂存，对S按绝对值赋值。
- 最终提交C只发送一次，应答未确认时完整读取95项实际参数；与目标一致才确认成功，不盲目重发提交。
- 明确拒绝、持续失败或设备重启时返回错误，不让未知配置直接进入运动。

此处参考实现为 `control/参数工具/源码/CarConfigClient.cs`，相应故障测试在 `CarConfigTests.cs`。不要直接把所有配置命令套进无条件重试循环。

## 4. 参数、标定与开机流程

本项目实际配置已经设置：

```json
{
  "chassis_config1_file": "control/参数工具/底盘参数.json",
  "chassis_result_recovery": true,
  "chassis_idle_preflight": true,
  "chassis_preferred_translation_unit": "CNT",
  "chassis_tx_padding_spaces": 32
}
```

合并时将这些键与对方现场配置合并，不覆盖其串口和雷达安装参数。代码默认开关与实际JSON可能不同，不能只合并Python而漏掉配置。

95项车端执行参数包括速度/前馈/PWM、起步过渡、八方向短长刹车表、制动保持、超时和已开放控制增益。它们写入RAM，断电后回到固件默认；电脑JSON永久保存，上电后读取核对或重新应用即可。

八方向距离系数由电脑将毫米转换为CNT后发送，底盘执行既有制动。**每个请求只换算一次，上位机不要再次扣刹车提前量。** 固件内置MM入口保留兼容；后续在电脑修改标定系数时，统一使用项目当前的电脑换算/CNT路径。

这些系数来自之前的现场长距离标定，属于当前载荷/地面的初值；安装雷达后可在JSON或集成终端内调整，无需改 `calibration.h` 再烧录。今天未重新拟合标定或刹车参数。

## 6. 给现场使用者的入口

优先窗口：`control/参数工具/底盘集成终端.exe`。

1. 退出占用底盘串口的其他工具，选择串口，点“连接并读取”。
2. 参数一致后，填写距离，选毫米或CNT，点击一个方向按钮。
3. 在表格直接编辑参数：执行参数点“保存并应用到小车”；只改距离系数点“保存到电脑”。
4. 点击红色停止或按Esc请求停止，确认车停稳后点击解锁。

原 `底盘参数工具_CONFIG1.exe` 仍可用于命令行对照；`start_chassis_parameters.bat`仍打开命令行工具。两种工具共用JSON，但同一时刻只能有一个程序占用底盘串口。操作日志与原始字节自动写入工具旁logs；窗口保存参数时在backups留存原文件。

具体操作及构建入口见 [参数工具使用说明](control/参数工具/使用说明.md)。普通使用直接运行exe，不需要编译或烧录。

## 7. 对方收到项目后要做什么

1. **合并运行代码与配置。** 保留本轮RESULT1、参数缓存和空闲握手实现，更新相关测试；保留对方现场串口、雷达配置及其他独立改动。GUI和命令行工具共用的C#源码需保持同一版本。
2. **补齐Python配置恢复。** 以C#实际实现和故障用例为依据，将第3.3节策略接入 `chassis_config1.py`，保持非阻塞发送、配置事务和停止互锁。这项改动在电脑端，无需更改固件。
3. **保持同一参数来源。** 人工和自动运动都使用 `chassis_config1_file` 指向的JSON，统一MM→CNT和执行超时配置。主上位机重新加载配置与独立工具修改后要同步，避免两边使用不同缓存。
4. **按现场证据配置导航。** 当前导航JSON仍有空底盘端口、`chassis_capability_mode=unknown`、`chassis_firmware_confirmed=false`，速度/制动验证和各方向验证范围仍未填写；不要把本次底盘功能测试自动等同于完整导航放行。现场按启动能力、端口及实际范围确认这些值。
5. **完成剩余现场收尾。** 确认临时LAT_RAMP_MS的最终值，补新窗口连接及一次短动作、运动中停止检查。已通过的八方向、写参和系数切换无需为了界面变化整套重跑。
6. **组装后进入雷达联调。** 处理最终载荷、雷达安装偏移、定位与动作后扫描，按需要更新电脑标定和执行参数。R/F旋转标定不在当前任务范围。

本次RESULT恢复解决的是传输丢报后的结果确认；此前旧电池条件下的连续重启仍属于供电问题，不能把它视为已经通过通信协议消除。现阶段没有已知需要再次烧录Arduino才能继续上述工作的缺口。
