## 装机前的一次升级

将 `control/` 内的 control.ino、utils.h、utils.cpp、calibration.h、runtime_config.h、runtime_accessors.h、runtime_parameters.h 一起复制到 Arduino 的 `control/` 工程目录，再上传。不能只复制 ino。源码使用已有 Arduino 环境，无新增 Arduino 外部库。

新版启动信息增加 `CONFIG=1 RAM=1 CRC=CCITT`。原 MM/CNT/PING 接口仍保留。当前主上位机启用电脑标定换算后发送 CNT，避免电脑新系数和底盘内置旧 MM 系数混用。

这轮未操作实际串口、未上传设备。底盘源文件与之前通过 UNO 编译的版本相同：Flash 30116/32256 字节，静态 SRAM 1458/2048 字节，剩余 590 字节；现场需观察实际运行余量。

## 后续如何调参

1. 打开本项目原有 `start_hardware_navigation.bat`，选择实际底盘端口。保存正确的固件能力，连接后读取底盘状态，确认空闲。
2. 展开“串口与指令”。点击“读取底盘参数”可读取全部 95 项并比较电脑文件；不会写入设备或发出移动。
3. 编辑并保存 `control/参数工具/底盘参数.json`。保留全部键，数值使用正常单位。停止导航后点击“重载并同步参数”。
4. 等待显示“底盘参数 CRC=…；与电脑不同项 0”。同步包含读取、暂存差异、一次提交和完整读回。全部默认值对应 CRC 十进制 5809；修改执行参数后 CRC 随之变化。
5. 用原来的人工动作入口进行所需验证。人工输入例如 D / 100 / MM，电脑先换算 CNT，再发送一次运动指令。自动导航同样使用此文件系数。

改 JSON 后必须重载；仅保存文件不会改变正在运行的上位机。参数不会在运动中热更新。设备断电或重启后，RAM 执行参数回到固件默认值；电脑文件仍保留，重新连接并执行“重载并同步参数”即可恢复。恢复过程不会自行续跑原动作。

如果只改距离系数，也使用同一按钮即可：电脑加载新系数，设备执行参数相同时只需读取核对，不会产生多余写入。自动导航按现有分段逻辑向下取整为 CNT，人工整数毫米输入按最近整数 CNT 换算，两者使用同一份方向系数。

## 参数分类与示例

| 希望调整的内容 | JSON 中的位置 | 如何生效 |
| --- | --- | --- |
| 右移等方向的距离比例 | `counts_per_mm.D`，其余对应 W/S/A/Q/E/Z/C | 电脑重新换算目标 CNT，编码器执行先验也使用新系数 |
| 起步过程 | `parameters.LAT_RAMP_MS` 等 | 同步到设备 RAM |
| 刹车提前量及适用区间 | `parameters.BRAKE_D_SHORT_LEAD`、同方向 LONG_LEAD/SHORT_TARGET/LONG_TARGET 等 | 同步到设备 RAM |
| 速度、前馈与 PWM 范围 | `parameters.LONG_*`、`LAT_*`、`DIAG_*`、`ROT_*` | 同步到设备 RAM |
| 动作超时、制动保持 | `parameters.RUN_TIMEOUT_MS`、`BRAKE_HOLD_MS` 等 | 同步到设备 RAM，PC 动作总时限相应增加 |
| 雷达安装偏置、导航速度上界、车体包络及方向验证范围 | 原有现场参数面板 / `navigation_config.json` | 使用原有现场参数保存流程 |

例如将 `counts_per_mm.D` 从 7.3864 改为 8.0，人工 D / 100 / MM 会从 739 CNT 改为 800 CNT。这只是解释系数作用，不建议无测量依据修改。执行参数共有 95 项，完整名称、范围与含义见 [CONFIG1 参数表](control/CONFIG1参数表.md)。无需把所有参数重新调一遍。

`navigation_config.json` 的 `chassis_config1_file` 已指向上述 JSON；其平移能力表中的系数在加载时由这份 JSON 更新，因此日常不需要在两处重复改数值。`chassis_tx_padding_spaces=32` 已接到实际发送链路。

## 同步与运动的处理规则

- 配置操作只在空闲时开始；同步期间拒绝新运动、通信检查和普通状态查询，急停继续可用。
- 每条 CFG 回复检查 CRC、随机标记、操作和索引。完整读回比较全部 95 项，确认一次提交后的实际值。
- READ/APPLY 完整成功后缓存确认状态。正常 MOVE 不发送 CFG 查询；执行参数变化、重连、检测到重启或同步失败时需重新确认。设备实际断电后应主动重新读取/同步，不能依赖一定收到启动横幅。
- 提交回报丢失时，设备可能已经应用参数。程序保持未确认状态，随后用“读取底盘参数”重新核对，不自动重发移动。
- 中断暂存后会尽力放弃事务；若通信中断导致放弃未到达，设备暂存事务在最后一次 B/S 后约 30 秒失效。遇到忙回复时先确认车辆空闲，等待事务失效再同步。
- PC 总等待时间至少为 14 秒，并至少比配置的底盘动作超时长 6 秒。默认导航安全边界及实测验证要求继续生效，参数同步成功不代表这些实测项目已完成。

## 烧录后最小实车验证轮次

目的：确认新版保持基本运动、远程执行参数真实写入、电脑距离换算生效，以及断电后能恢复配置。本轮不重新做完整刹车拟合或距离标定。预计约 10～15 分钟，按实际通信和操作速度安排。

### A. 烧录与测试入口

烧录对象是 Arduino UNO 底盘。源码取本项目 `control/`，将以下 7 文件一起复制到 Arduino 的 `control/` 工程目录：`control.ino`、`utils.h`、`utils.cpp`、`calibration.h`、`runtime_config.h`、`runtime_accessors.h`、`runtime_parameters.h`。在 Arduino IDE 中打开 `control/control.ino`，选择 Arduino Uno 和对应上传端口再上传。JSON、exe、Python 文件不烧进 Arduino；本轮不涉及 ESP32 雷达烧录。

上传后关闭 IDE 串口监视器和占用底盘 COM 的其他程序。先用本项目 `control/参数工具/底盘参数工具_CONFIG1.exe` 测试，不要求雷达同时在线。选择实际底盘无线串口，后面的 READ、LOAD、APPLY 和运动指令均在这个工具内输入，每条按回车，收到结束结果后再输入下一条，不用定时连发。

测试工具与固件不必位于同一个目录：Arduino 中的副本仅用于编译上传；参数仍编辑本下载项目中 exe 旁的 `底盘参数.json`。日志自动保存在该 exe 旁的 `logs/`，包含事件文本与原始接收字节。

### B. 默认配置与八方向检查

1. 输入 `READ`。若 JSON 仍为随项目提供的默认配置，应读到 95 项、CRC=5809、与文件不同项=0。启动时若能看到横幅，应有 `CONFIG=1 RAM=1 CRC=CCITT`；连接时错过横幅无需为了看它再次复位，成功的 CONFIG1 回读可确认接口。
2. 输入一次 `PING`，确认握手成功。
3. 保持车体方向不变，在足够空旷的平面依次执行下列短动作，每条等完成再继续：

```text
W 100 MM
S 100 MM
A 100 MM
D 100 MM
Q 100 MM
C 100 MM
E 100 MM
Z 100 MM
```

相反方向成对，便于限制场地占用；不要求最后精确回到原点。检查方向正确、一次指令只动一次、每次正常停下，并收到对应模式的完整 TARGET 结束报告，没有重启或通信超时。不以肉眼测得的毫米精度或几 CNT 的停点误差作为这轮失败标准。

### C. 一次停止功能检查

留出此前 D1400 测试所需的右侧空间，输入 `D 1400 CNT`，开始移动后按 Esc。检查车停止，工具保持锁定且不补发动作；若收到完整结束报告，原因为 EMERGENCY。车体确已停稳后输入 `CONFIRM` 解锁。若这次已正常 TARGET 结束，说明按键晚了，未验证到运动中停止，可重做一次。停止报告丢失时保留日志，不把缺失报告当成已确认成功。

### D. 真正写入 Arduino 的远程调参

记下 `parameters.LAT_RAMP_MS` 原值；当前默认是 500。只将这一项临时改成 700，保存 JSON，其余参数保持原值。输入：

```text
LOAD
APPLY
READ
D 100 MM
```

检查 APPLY 后完整回读、与文件不同项=0，配置 CRC 相比此前变化，并且 D 动作仍正常。READ 的一致结果证明电脑目标参数与设备读回值相同；不要求靠肉眼分辨 200 ms 的起步差异。若初始文件已有个人调整，测试前记下原值，最终恢复个人原值。

### E. 断电与恢复

在车停稳、上一条操作已结束后，对底盘实际控制器断电再上电。只关闭串口或只断开电机电源不能代替这一步；如果 USB 仍在给 Arduino 供电，需要确认控制器确实经历了断电。重新连接工具，电脑 JSON 暂时保留 LAT_RAMP_MS=700：

```text
READ
APPLY
READ
```

若其余参数均为默认，第一次 READ 应显示 LAT_RAMP_MS 的设备值 500、电脑值 700，共 1 项不同，设备 CRC 回到 5809；APPLY 后再 READ 应恢复不同项 0。这个结果确认文件保留、设备 RAM 重置和无线恢复三条链路。若有其他个人运行参数，重启后的不同项数可能多于 1。

然后将 LAT_RAMP_MS 改回测试前原值，保存，输入 `LOAD`、`APPLY`、`READ` 恢复。

### F. 电脑端距离系数试验

记下 `counts_per_mm.D` 原值（随项目提供的值为 7.3864），临时改为 8.0，保存后输入：

```text
LOAD
D 100 MM
```

工具应打印发送 CNT=800，ACK/DONE 的请求量也应为 800 CNT；原系数 7.3864 对应 739 CNT。此项只验证电脑换算链路，不以尺子测得恰好 100 mm 为通过条件，也不把临时 8.0 作为新标定结论。95 项设备执行参数 CRC 不因电脑距离系数改变而变化。

改回测试前 D 系数、保存，再 `LOAD`。输入一次 `D 100 MM`，在原系数 7.3864 下应重新发送 739 CNT。最后 `READ` 确认执行参数仍与文件一致。

### G. 主上位机入口确认

有条件连接本项目正常需要的设备时，退出独立工具，打开原主上位机，在底盘空闲状态点击“读取底盘参数”和“重载并同步参数”，确认显示不同项 0。主上位机与独立工具不可同时占用同一底盘 COM。若只有底盘在线，先完成 B～F；主上位机界面的连接验证留到雷达一起接入时完成，不将独立工具通过写成整套雷达导航通过。

留存这一轮 `control/参数工具/logs/` 中的日志，并记录八方向、停止、执行参数写入、断电恢复、电脑系数切换各项是否通过。测试结束应恢复临时改动，保留原标定系数和原控制参数。

## 首轮 CONFIG1 实车反馈：回传截断，测试暂停

用户反馈发生于八方向检查开始阶段。实际执行工具位于项目外的“主线指令发送器”目录，端口 COM8；已核对该工具 exe 和参数 JSON 与本项目 control/参数工具 中对应文件的 SHA256 分别相同，所以本轮不能归因于工具版本或配置文件差异。后续仍统一使用本项目内的路径。

已收到的证据：

- 配置摘要回复 `@CFG,I,...,1,95,5809`：车上支持 CONFIG1，报告 95 项及默认执行参数 CRC。
- READ 完整收到起始索引 0、8、16、24、32、40、48、56 的页面；索引 64 页超时。之后发现其不完整尾部 `@CFG,G,FEA2BDB4,64,600,1200,5`，没有完整 CRC 或行结束，因此本次全表读取失败。
- 随后 PING/PONG 成功，W 动作前配置摘要也成功。
- W100MM 在电脑按 7.1775 CNT/mm 换算为 718CNT，收到 `@ACK,W,718,CNT` 和 START/W，工具只发送一次 MOVE。
- 启动诊断报告 `FREE_RAM_START=313`。这是该调用时刻的空闲堆栈间距，不能仅凭这一数值认定已发生内存耗尽；仍需结合后续运行证据评估。
- 结束报告只收到从 `=CNT,BRAKE=640.75,ENC=748.25,...,Q4=744` 开始的后半段，缺少 `@DONE`、方向、原因和请求标识。工具没有接受它为完成，也没有重发 MOVE。
- 后续两次 S100MM 均被“上一运动未确认”互锁拦截，尚未发送给车辆。八方向测试未完成。

结论：新固件接口与目标换算已得到现场证据；完整参数回读和运动结束确认尚未通过。这一片段没有重复启动横幅，不能据此认定复现了之前的重启问题。参数页尾部缺失和 DONE 前部缺失需要继续排查接收链路；目前证据不足以定位到无线模块、供电或主机某一环节。START 诊断在固件 LOG=0 时仍无条件输出，增加了回传量，但尚无证据证明它就是本次截断的根因。

下一步先确认车辆停稳，保留当前运动互锁；只运行三次 READ（各次等结束后再发下一次，不发 MOVE），记录是否总在相同索引截断以及完整回读成功次数。READ 是只读操作，现有工具允许在运动结果未确认时使用，无需为了它输入 CONFIRM。配置全表回读稳定前，暂停后续八方向、远程写参和标定。不要把残缺 DONE 拼成成功报告或通过重发原动作补救。


### 改动前的体验反馈：等待明显变长

用户补充：本轮延迟和等待感明显长于此前使用。核对当前独立工具实现后，存在以下可确定的软件开销；这些是代码中的等待值，不是本次日志实测的端到端耗时。

| 场景 | 当前实现与影响 |
| --- | --- |
| 完整 READ | 前后 2 次 I 加 12 次 G，共 14 次请求；每次 Exchange 都重新等待至少 500 ms，因此仅静默等待就至少 7 秒，另外还有串口/无线往返时间 |
| 单次运动起步前 | 新增 CFG 摘要查询前至少 500 ms，原有 PING 前至少 500 ms、PONG 后至少 250 ms；通信首发全部成功时，仅这些等待合计至少 1.25 秒，尚未包含往返时间。旧工具对应的原有等待至少 0.75 秒 |
| 参数页残缺 | 当前页等待 4 秒后报告超时；本次 READ 在索引 64 页触发此等待 |
| 运动 DONE 残缺 | 默认从 MOVE 发出后最多等待 14 秒，完整匹配 DONE 到达则提前返回；本次因为缺少完整 DONE，走到了超时。不是车辆必须运动或停住等待 14 秒 |

结论：等待变长同时包含新核对流程的正常开销，以及本次回传截断引发的超时开销。当前每页统一等待 500 ms 的实现较保守，应在解决回传完整性时一并优化；不能简单缩短 DONE 超时来改善表观速度，也不能取消运动结果确认。后续验证同时关注完整回读成功率、指令到起步的延迟与完整 DONE 到达后的界面响应。此处记录当时的耗时分析；后续已按用户要求取消每次运动前的参数查询，见下文。


## 参数确认缓存更新：取消每次运动前查询

用户要求：连接开始或主动发指令时读取参数；平时执行动作时不重复读取。本次仅修改主上位机与独立参数工具，Arduino 源码不变，无需重新烧录。

- 新开连接未确认：先 READ 或 APPLY，完整回读成功且与电脑执行参数一致后允许动作。
